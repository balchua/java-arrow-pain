### Key Observations — Before vs After (Streaming vs Batch-Accumulation)

| Metric | Before (batch accumulation) | After (streaming) | Reduction |
|---|---|---|---|
| Type A Arrow off-heap peak | 348 MB | **24.5 MB** | **−93%** |
| Type B Arrow off-heap peak | 348 MB | **24.5 MB** | **−93%** |
| Type C Arrow off-heap peak | 562 MB | **38.1 MB** | **−93%** |
| Total Pod Impact (Type A) | ~1,500 MB est. | **1,086 MB** | Fits in 4 GB pod |
| 10M row file (projected) | ~8 GB Arrow | ~150 MB Arrow | **OOM → fits** |

> **`Off-heap stream` is the key new metric** — sampled at each 65,536-row batch flush during
> `parseStreaming()`. It confirms the parser reuses the same `VectorSchemaRoot` rather than
> accumulating all batches. The `HWM` (allocator lifetime high-water mark) is only marginally
> higher because a single batch is live while the next is being filled.

> **`Write ms = 0`** is expected: Arrow IPC Stream writes happen inline during `BatchConsumer.accept()`
> callbacks inside the parse loop. The `finish()` call only flushes and closes the stream writers.

> **Java heap delta is larger** (26–64 MB vs 8–42 MB before) because DuckDB query planning now
> runs against live tables rather than registered Arrow views, requiring more JVM coordination.
